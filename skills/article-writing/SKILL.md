# 写文章

## 什么时候用

用户要的是一篇**成品**，不是一段回答：有开头结尾、能直接发出去或交上去。

边界要先分清：

- 用户说"介绍一下 X"——可能只是想听你讲，不是要文件。先问清楚，或者直接在回复里给。
- 用户说"写一篇 X""写到 out/ 下"——要文件，用 `write_file` 落盘。
- 用户给了字数——那是硬要求，写完要数。

## 先定三件事

动笔前把这三件事在心里定下来。定不下来就先问用户，别硬写。

1. **读者是谁**：完全不懂的、懂一半的、还是同行。同一件事对这三种人写法完全不同。
2. **读者读完要干什么**：知道一个新概念？照着做一遍？被说服？没有这个，文章就是流水账。
3. **字数**：800 字的文章只能讲透一个点。想讲三个点就得写到 2400 字，或者砍掉两个。

## 结构

默认用这个骨架，按需增删：

```
标题          —— 具体，含关键词，不要"浅谈 X"这种
开头（1-2 段） —— 一个具体的场景 / 问题 / 反常识的事实，不要"随着……的发展"
主体（2-4 节） —— 每节一个小标题，一节只讲一件事
结尾（1 段）   —— 收回到开头那个点，或者给一个可执行的下一步
```

**一节只讲一件事**是全部规则里最重要的一条。一节里塞两个论点，读者一个都记不住。

## 行文

- **具体压过抽象**。"性能提升明显" 不如 "从 1.2 秒降到 0.3 秒"。
- **短句。** 一句话超过 40 字就拆开。中文尤其经不起长定语。
- **少用形容词。** "非常强大的功能" 删掉形容词还剩什么？剩下什么就写什么。
- **主动语态。** "配置被加载了" 不如 "maa 加载配置"。
- **不写过渡废话。** "接下来我们来看一下" —— 直接看。
- **术语第一次出现时解释一句**，除非确定读者是同行。

### 开头别这么写

- "随着人工智能技术的飞速发展……" —— 万能开头等于没有开头。
- "在当今这个 XX 的时代……" —— 同上。
- "X 是一个非常重要的概念。" —— 重要在哪？直接说。

好的开头要么给画面（"上周我把一个 40 行的脚本重写成 200 行，跑得快了三倍"），
要么给冲突（"所有人都说该用 A，可我这半年用的是 B"）。

## 写完检查

1. **数字数。** 用户要 800 字，700 和 900 都可以，400 和 1500 不行。
   ```bash
   python -c "import sys;print(len(open(sys.argv[1],encoding='utf-8').read()))" out/article.md
   ```
   中文按字符数算，标点也算。
2. **只读开头和结尾。** 这两段立不住，中间写得再好也没用。
3. **每节自问"这节删掉，文章少了什么？"** 答不上来就删掉。
4. **念一遍。** 读着别扭的地方就是该改的地方。

## 落盘

- 路径听用户的；没说的话，标题起个 slug，放 `out/` 下。
- Markdown 格式。标题用 `#`，小节用 `##`，别跳级。
- 写完把路径和字数告诉用户，别把全文再贴一遍——文件已经在磁盘上了。
