# 任务规划

## 什么时候用

**两个动作能做完的事不要规划。** 规划本身有成本，三步以内的任务列清单纯属浪费。

要规划的信号：

- 步骤数 ≥ 3，或者现在还不知道有几步。
- 要动多个文件 / 多个模块。
- 中途可能失败，失败了要能回到某个已知点。
- 用户明确说了"先做个计划"。

用 `write_todos` 列，而不是在回复里写一段"我打算先……再……"。前者是可以逐条勾掉的
状态，后者是聊完就没的一段话。

## 拆法

拆到**每一步做完都有东西可看**为止。

> 差：实现用户认证 → 反正下一步还是写代码，看不出进度
> 好：定义 User 模型和迁移 → 写登录接口 → 写 token 校验中间件 → 给登录接口加测试

判断标准：**这一步做完，能不能说一句"现在 X 可以了，但 Y 还不行"？** 说不出就还得拆。

### 第一个 todo 应该是调研

除非你已经很确定怎么做，否则第一项就写"读 X 和 Y，确认 Z 的做法"。调研本身是一步，
不该藏在脑子里——不写出来就容易跳过，跳过就会返工。

### 最后一项应该是验证

"跑一遍全量测试""手动跑一次确认输出对"。没有这一步的计划不完整，
因为"写完了"和"能跑"不是一回事。

## 执行

1. **做完一步就标一步。** 别攒到最后一起标——攒着就没有进度信息了，
   出问题时也不知道是从哪一步开始歪的。
2. **发现计划错了就改计划，别硬走。** 第三步做到一半发现第二步的前提是错的，
   回去改，别为了"按计划完成"往下堆。
3. **卡住了就写在清单上。** 把「被 X 挡住」当一条 todo 写下来，比在脑子里反复琢磨
   更容易看清问题出在哪。
4. **一次只做一件事。** 同时开三条线，最后一条都没收尾。

## 受阻和返工

- **受阻**：说清楚**被什么挡住**，以及需要什么才能继续。"网络不通" 不如
  "需要 X 服务的 API key，没有它第 3 步做不了"。
- **返工**：发现自己做错了就直说，别悄悄改掉当没发生过。已经汇报过的结论要更正。
- **不要在受阻的步骤上死磕。** 绕不过去就先做后面的独立步骤，但要在清单上留痕。

## 汇报节奏

- 计划定完，先告诉用户大概要几步、每步产出什么。方向错了这时候改最便宜。
- 中间只在**有实质进展或者卡住**的时候说，不要每勾掉一项就汇报一次。
- 全部做完给一个总结：做了什么、没做什么、哪些没验证过。**没做什么同样要说。**
