# 写代码

## 什么时候用

任务落在某个代码仓库里，成败以"能不能跑"为准，而不是"看起来对不对"。

## 铁律

**没跑过就不算完成。** 这句话没有例外。

- 说"已修复"之前，那个失败的命令必须已经变成成功。
- 说"测试通过"之前，得真跑过测试，并且看到通过的数字。
- 跑不了（缺依赖、缺密钥、环境不对），就明说跑不了，别把"应该能行"说成"能行"。

自测通过和实际通过是两回事。汇报时把区别讲清楚。

## 动手之前

1. **先读再改。** 改任何文件之前先 `read_file` 读一遍。凭猜测覆盖别人的代码是最贵的错误。
2. **找到这个仓库自己的写法。** 命名、缩进、错误处理、注释密度——照着邻居写。
   引入一套跟周围格格不入的风格，比写错一个函数更麻烦。
3. **搜索已有实现。** `grep` / `glob` 先找一遍：这个功能是不是已经有人写过了？
   重复造一个半成品比不写更糟。
4. **改动范围跟需求对齐。** 修一个 bug 就只修那个 bug。顺手重构会把 diff 变成一锅粥，
   让 review 的人无从下手，也让出问题时无法回滚。

## 改代码

- **最小改动。** 能改三行就别改三十行。
- **别动无关的格式。** 不要顺手把整个文件重新排版——那会让 diff 里全是噪音。
- **保持向后兼容**，除非用户明确要求破坏性变更。
- **删代码要确认没人用。** `grep` 一遍再删。
- **不确定的地方写注释说明，别写注释掩盖。** `# 这里必须这样，因为 X` 是好注释；
  `# 处理数据` 是废话。

## 加测试

- **测行为，不测实现。** 断言"输入 A 得到 B"，而不是"调用了内部函数 C"——
  后者会让重构寸步难行。
- **测试名字要说明白测什么。** `test_写错的键会被指出来` 比 `test_config_3` 强得多。
- **一个测试一个失败原因。** 一个测试里断言十件事，挂了不知道该修哪儿。
- **先让它红。** 写完测试先跑一遍确认它真的会失败——不会失败的测试等于没有测试。

## 验证顺序

从快到慢，能早点停下来就早点停：

```bash
# 1. 语法 / 导入能不能过
python -c "import 包名"

# 2. 相关的那几个测试
pytest tests/test_相关.py -q

# 3. 全量测试
pytest -q

# 4. lint / 格式化
ruff check . && ruff format --check .
```

## 汇报

- 说清楚**改了什么、为什么**，别只贴 diff——diff 用户自己会看。
- **失败就说失败**，把报错原样贴出来。藏起来或者换个说法，代价是用户带着一个错的认知继续往下走。
- **跳过了什么也说明**。"没跑集成测试，因为需要真数据库"——这一句比十句"已完成"有用。

## 不要做

- 不要为了让测试变绿而改测试的断言（除非断言本身就写错了，那要说明理由）。
- 不要注释掉报错的代码了事。
- 不要加 `try: ... except Exception: pass`。
- 不要在没被要求的情况下加依赖——每多一个依赖都是长期的负担。
